## HTTP contract

1. `POST /api/receipts/upload` existing authenticated private upload; response `receipt_key`.
2. `POST /api/receipts/analyze`, JSON **only** `{ "receipt_key": "/api/receipts/evidence-123-abcdef.png" }`.
3. Cookie session + exact Origin gate; full Staff/Owner session. Staff own-user/current assigned branch; Owner registered asset access. Revalidate session, actor/role/branch and asset ownership after inference. No arbitrary URL, image input, client system/provider/model/history/session overrides.
4. `200`: `{receipt_key, engine:"widya-hermes-vision", runtime:{provider,model}, requiresHumanReview:true, text, suggestions:{amount:<exact IDR digit string|null>,date:<ISO|null>,merchant:<string|null>},ambiguity,warnings}`.
5. Both `/api/widya/extract` and `/api/dewi/extract` return `410 WIDYA_RECEIPT_LEGACY_RETIRED`; no storage/inference side effect. Local OCR modules remain standalone/unmounted, not a fallback/default.

Amounts cross-checked against explicit TOTAL transcription, including conflicting/unreadable totals; cash tender/change excluded. Invalid/ambiguous values null, never zero/default guesses. Dates cross-check ISO or DD/MM/YYYY / DD-MM-YYYY transcription; conflicting or invalid candidates remain null. Transcription is still model-generated, not a guarantee of receipt authenticity.

## UI

Checkbox `Saya sudah memeriksa foto dan saran nota ini` + `Terapkan saran` apply only amount/date/merchant. Identity/upload/receipt guard rejects stale results. Payment/category/items are not inferred. Financial submit/approve remains separate. Failure preserves existing form values and successfully uploaded receipt. Image text never executes; providers may still misread adversarial documents, so human photo review remains mandatory.

Photos are processed on VPS and transmitted to configured provider through 9Router; not local-only privacy. UI discloses this. No real receipt or production financial writes were used in verification.
