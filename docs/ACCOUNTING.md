# SiPeKA accounting foundation — parent integration contract

Foundation implemented; HTTP/UI and startup verification integrated in server.js. See ACCOUNTING-HTTP.md for actual routes and independent release verification. Historical proposed integration details below are design context, not live route names.

## Supported scope
Balanced immutable posted journals from explicitly reviewed APPROVED SETOR_NOTA operational cash sources; append-only linked reversal; exact integer IDR strings; posted movement trial balance. No draft workflow, accrual recognition, opening import, tax engine, complete neraca, payroll posting or bank settlement. Migration creates account definitions, not balances. Existing operational approval never automatically posts a journal. Owner separately invokes posting after source classification/evidence review. Header actor_id derives from a valid full Owner session inside PG; approved_at records explicit approval/posting atomically. One source = one journal; one original = one reversal. Correction after reversal requires a future reviewed adjustment contract, not reusing the old transaction.

Production read-only CoA inventory verified: 4101 REVENUE; 5101,5102,5103,5104,5120,5310,5400 EXPENSE. Separate accounting accounts preserve operational IDs. Maintenance explicitly installs reviewed revenue/expense definitions and category maps. No automatic map/backfill. Standard asset/liability/equity definitions: 1101 cash,1102 bank,1103 QRIS clearing,1201 AR,1301 inventory,1401 prepaid,1501 fixed assets,1591 contra-asset depreciation,2101 AP,2201 deferred revenue,2301 loans,3101 capital,3201 retained earnings. No tax liabilities inferred. Normal debit types ASSET/EXPENSE except contra-asset 1591; others credit. Trial balance returns signed debit-minus-credit movements, not asserted normal/ending balances.

Funding identity is an explicit maintenance mapping per branch/method with reviewed evidence. CASH_DRAWER and BANK_TRANSFER require ASSET; maintenance must choose actual cash/bank accounts (engine does not validate financial institution identity). QRIS strictly uses 1103 clearing, never 1102 bank; outflow unsupported. No net settlement/fee split inferred. Current canonical 1103 shared account distinguishes branch/fund in source snapshot; multiple providers/named bank ledger subaccounts require future versioned account-role extension. Category mapping only REVENUE for income, EXPENSE for expense. Owner must exclude capital, loans, transfers, assets/prepayments and unpaid/unearned items from this limited cash-source mapper. Unknown source blocks; not suspense/plugs. Memo/receipt key omitted from source snapshot; no individual payroll source mapping.

## Parent-only HTTP integration (proposed, not existing routes)
- `POST /api/accounting/journals/post`: Owner cookie session + exact Origin/CSRF; call `post(pool, authenticatedSessionToken, body)` only after explicit human approval. Body `{sourceType:'CASH_TRANSACTION',sourceId,fundId,accountingDate:'YYYY-MM-DD',idempotencyKey,evidence}`. IDR comes from DB source, never body. Response `{id}`. Whitelist body fields. Never accept actor/session token/provider intent from body; never expose this mutation through autonomous Widya tool access.
- `POST /api/accounting/journals/:id/reversal`: same gate; body `{sourceType:'REVERSAL',sourceId:originalJournalId,accountingDate,idempotencyKey,evidence}`. Reversal cannot precede original date.
- `GET /api/accounting/trial-balance?start=YYYY-MM-DD&end=YYYY-MM-DD&branchId=...`: Owner-only, call `trialBalance(pool, authenticatedSessionToken, {start,end,branchId:null|string})`. Inclusive accounting-date filters (WIB business dates supplied explicitly; not UTC created_at conversion), archived branch history not excluded. Repeatable-read snapshot; `rows[{id,code,name,type,debit,credit,netMovement}]`, string `totalDebit,totalCredit,journals,lines`; `basis='POSTED_RECORDED_CASH_BASIS_MOVEMENTS'`, `openingBalances='MISSING'`, `neracaComplete=false`, notices. Unknown branch currently produces empty movement scope; parent should validate historical branch ID rather than imply branch existence. No ending-balance field.
- Staff/unauthenticated denied before all handlers, including downloads. Parent must test actual cookie/Origin/session expiration, forged actor, explicit human approval UI and logout; module PG role tests do not certify HTTP.

## Maintenance/security gates
Migration 007 maintenance-only; runtime cannot CREATE or INSERT/UPDATE/DELETE accounting tables. Runtime gets SELECT four accounting tables, EXECUTE three pinned SECURITY DEFINER functions (Owner authentication, posting, read-only preview); PUBLIC execute revoked. Auth token binds actor; runtime compromise able to obtain Owner tokens remains inside trusted application boundary, not a cryptographic human-consent proof. Migration owner must be maintenance role, never runtime. Schema owner maintenance; no runtime CREATE. Do not apply default broad INSERT/UPDATE grants after migration. Posted header/lines/account/maps/funds updates/deletes blocked by immutable triggers even maintenance. Deferred DB balance constraints require two lines and exact numeric debit=credit; unique keys and global advisory xact lock serialize retries and posting. No operational workflow changes.

Period-lock table read by posting. Closing UI/API deferred. Maintenance closing must acquire `pg_advisory_xact_lock(1397313612::bigint)` in the same transaction before insert; otherwise close/post race is NOT enforced. No runtime closing grant. Global lock intentionally favors correctness over throughput.

Required parent handoff edits BEFORE release: migration runner accounting table/type/guard/ACL/function-search-path verification; existing runner only verifies migration checksum + operational guards. Add startup fail-closed coverage for missing/disabled accounting guards. This new migration file means un-migrated PG startup checksum mismatch by design; existing SQLite remains operational-only, accounting unavailable. New engine only two-line reviewed cash sources/reversals; general/manual multi-line persistence deferred (`validateLines` is pure validation only). Add source coverage/reconciliation (approved source count vs posted IDs) before calling any report complete. Account grouping legal entities not yet configured; all-branch totals are ledger movements, NOT legal-entity consolidation.
